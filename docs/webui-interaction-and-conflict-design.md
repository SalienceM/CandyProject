# CandyProject — Web UI 交互设计 & 冲突规避方案

---

## 一、角色与视图

```
打开 Web UI
    ↓
选择角色
├── user（开发者/执行者）→ 任务列表、进度更新、文件提交
└── manager（管理者）   → 汇总看板、统计报告、归档导出
```

---

## 二、核心设计原则：两类数据严格分离

**冲突的根本原因**：Web UI 和开发者的本地提交写入同一文件。

解决方法：**从设计上让两类写入永远不触碰同一文件**。

```
仓库文件分两个命名空间：

.candy/                     ← Candy 独占写入，开发者不碰
  tasks/
    TASK-001/
      meta.toml             ← 任务元信息（由 Candy 服务写）
      progress.md           ← 进度记录（Web UI 写）
      tracelog.md           ← 追踪日志（Web UI 写）

src/ docs/ 等业务目录       ← 开发者独占写入，Candy 只读
```

规则：
- `.candy/` 目录：**只有 Candy 服务写，开发者不提交这里** → Web UI 写入零冲突
- 业务目录：**只有开发者写，Candy 只读取** → 开发者工作流零干扰

`.gitignore` / SVN `svn:ignore` 不忽略 `.candy/`，让它被 VCS 正常追踪，
但在团队约定 / pre-commit hook 中阻止开发者手动修改它。

## 三、User 角色：两类操作的设计

### 3.1 轻量更新（进度 / Tracelog）

**场景**：用户在 Web 上写今天做了什么，遇到什么问题。

```
Web UI 输入框
    ↓
后端追加写入 .candy/tasks/TASK-001/progress.md
    ↓
服务端 git commit（使用独立的 service account）
    ↓
git push
```

**为什么不冲突**：
- `.candy/tasks/` 下的文件只有 Candy 服务写
- 开发者不会 push 修改这个目录
- 即使多个用户同时写不同任务，文件路径不同，互不影响

**并发保护**（同一个任务被两人同时写）：
```
服务端对每个任务文件加文件锁（flock / asyncio.Lock）
写入队列化：先到先写，后者追加，不覆盖
```

---

### 3.2 文件提交（上传实质性材料）

**场景**：用户需要提交设计稿、文档、代码变更等业务文件。

**关键判断**：这类操作本质上是 VCS 的写操作，风险高于轻量更新。

#### 流程设计

```
① 用户在 Web UI 点击"提交文件"
        ↓
② 后端在服务器创建隔离工作区
   git worktree add /tmp/candy-work-{session_id} {branch}
   （或 svn checkout 到临时目录）
        ↓
③ 展示文件树，用户导航到目标目录
        ↓
④ 用户上传文件 / 在线编辑
        ↓
⑤ 后端执行提交前检查：
   git fetch origin {branch}
   git merge-base --is-ancestor HEAD origin/{branch}
   → 如果远端有新提交：先 rebase/merge，再检测冲突
   → 无冲突：继续
   → 有冲突：中止，告知用户"远端已有更新，请先同步"
        ↓
⑥ git commit + git push
        ↓
⑦ 清理临时工作区
   git worktree remove /tmp/candy-work-{session_id}
```

#### 冲突处理策略

| 情况 | 处理方式 |
|---|---|
| 用户修改的文件，远端无变更 | 直接提交，成功 |
| 用户修改的文件，远端也有变更（内容不同行） | 自动 merge，成功 |
| 用户修改的文件，远端也有变更（同行冲突） | **中止**，提示用户下载最新版后重新上传 |
| 用户提交时网络中断 | 工作区保留，用户刷新后可继续 |

**SVN 的额外优势**：
SVN 原生支持文件锁（`svn lock`）。
对于文档、设计稿等二进制文件，Candy 可自动加锁：
```
用户开始编辑 → 后台 svn lock 该文件
其他人尝试编辑 → 提示"该文件已被 张三 锁定"
用户提交完成 → 自动 svn unlock
```

## 四、服务端 Git 操作的隔离架构

```
Candy Server
├── 主进程（FastAPI）
│   └── 接收 Web UI 请求
│
├── VCS Worker（独立进程 / 线程池）
│   ├── 每个"文件提交会话"使用独立 worktree
│   ├── .candy/ 写入使用单独的串行队列（避免并发 push 冲突）
│   └── 所有 push 失败自动重试（指数退避）
│
└── 工作区管理
    ├── /tmp/candy-work-{session}/  ← 文件提交用，用完即删
    └── /var/candy/repo-cache/      ← 只读镜像，用于浏览文件树
```

**为什么用 worktree 而不是 clone**：
- `git worktree` 共享 `.git` 对象库，磁盘开销小
- 多个并发提交可以在不同 worktree 中独立操作，互不影响
- 比多次 `git clone` 快得多

## 五、User 视角的完整 UI 流程

```
登录 → 选择 User 角色
        ↓
任务列表（按状态分组：进行中 / 待处理 / 已完成）
        ↓
点击某个任务
        ├── [写进度]  → 富文本输入框 → 提交 → 追加到 progress.md → 后台 commit
        ├── [写日志]  → 同上 → 追加到 tracelog.md → 后台 commit
        └── [提交文件] → 文件树导航 → 上传/编辑 → 冲突检测 → commit+push
```

**进度/日志写入**：
- 追加写入，不覆盖，带时间戳和作者
- 格式示例：
```markdown
## 2026-03-19 14:32  @zhangsan
完成了登录模块的单元测试，覆盖率 87%。
待处理：集成测试环境配置。
```

**文件提交引导**：
- 根据任务类型给出目录建议（可配置）
- 例如 TASK-001 关联 `src/auth/`，直接打开到该目录
- 提交前展示 diff 预览，用户确认后再 push

## 六、冲突规避总结

| 操作类型 | 冲突风险 | 规避方式 |
|---|---|---|
| 写进度 / 日志 | **零风险** | 文件在 `.candy/` 独占命名空间，开发者不触碰 |
| 多人同时写同一任务进度 | **低风险** | 服务端队列化，追加写入 |
| 提交业务文件，无并发 | **低风险** | 提交前 fetch 检测，rebase 处理 |
| 提交业务文件，有并发 | **中风险** | worktree 隔离 + 冲突检测 + 中止并提示 |
| SVN 二进制文件 | **低风险** | 自动 `svn lock` 独占编辑 |

**根本原则**：
> Candy 服务只独占写 `.candy/` 目录，业务代码目录永远交给开发者用本地 VCS 工具操作。
> Web UI 的"文件提交"是引导性的，不是强制替代本地 VCS 客户端。
